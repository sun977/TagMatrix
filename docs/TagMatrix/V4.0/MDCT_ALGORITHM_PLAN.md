# V4.0 打标模式优化与多维共识打标算法 (MDCT) 架构蓝图

> **文档状态**：架构探讨与演进规划（草案）
> **目标阶段**：V4.0
> **核心议题**：针对现有打标模式（单标签、混合模式）中“标签优先级碰撞”问题的算法升级，旨在告别机械的 ID 比对，引入更精准的数据导向与 AI 辅助裁决机制。

---

## 1. 现状痛点分析

在 V3.x 版本的 `taskengine_service.go` 中，打标引擎的逻辑非常健壮：AST 布尔树解析器 (`matcher.go`) 只负责计算匹配结果，优先级排序和打标模式分发完全由外层任务引擎接管。

然而，在处理“多规则碰撞”（即一条数据同时符合多个标签的打标条件）并需要决出“唯一标签”或“主标签”时，目前的排序机制存在明显的不足：

1. **人为 Priority 利用率极低**：所有的规则默认优先级（`Priority`）都是 `0`，业务人员极少去精细化配置。
2. **兜底机制过于粗暴**：当 `Priority` 相同时，系统只能依靠比对规则的 `ID`（即创建时间的先后）来决定谁胜出。这种机制完全脱离了数据本身，容易产生“后建的垃圾规则覆盖了核心规则”的线上事故。
3. **缺乏智能熔断**：在遇到难以决断的业务边界时，系统会机械地执行上述粗糙逻辑，而缺乏人工复核或智能介入的通道。

---

## 2. 演进目标：一切以客观数据为准

为了让打标更准，我们否决了单纯基于“统计学稀有度 (IDF)”这种容易导致业务偏差的算法。真正的算法升级必须遵循：
*   **尊重配置特权**：人工设置的最高优先级不可僭越。
*   **深挖业务特征**：依据规则的严谨度来判定确信度。
*   **审视数据本身**：数据质量越高，标签可信度越大。
*   **好钢用在刀刃上**：引入 AI，但绝不滥用，仅将其作为平局的“最终仲裁官”。

---

## 3. 多维共识打标算法 (Multi-Dimensional Consensus Tagging, MDCT)

我们计划在 V4.0 中引入一套不破坏现有 AST 架构、纯后端实现的**多维归一化打分算法**。

综合得分公式如下：
```text
FinalScore(Record, Rule) = 
      W1 * PriorityScore(Rule)         // 人为静态权重 (基础决定权)
    + W2 * ComplexityScore(Rule)       // 规则逻辑深度打分 (客观数据复杂度)
    + W3 * CompletenessScore(Record)   // 数据置信度打分 (客观数据质量)
    + [延迟计算] W4 * AIConsensusScore // AI 语义裁决分 (仅在基础分相近时触发)
```

**【新增需求与评估】：打分权重 (W1~W4) 自定义配置方案**
*   **需求描述**：系统应当允许用户（如系统管理员或高级业务人员）根据不同的业务偏好和数据情况，通过前端页面自定义 W1、W2、W3、W4 这四个维度的权重比例。
*   **方案评估与实施设计**：
    *   **配置层 (UI & DB持久化)**：在【全局系统设置】或具体的【任务参数配置】页面新增“打分维度权重配置”卡片。默认给出系统推荐值（例如为了确保优先级统治权，W1=1000，W2=10，W3=10，W4=100），并提供滑动条或数字输入框供用户微调，配置落盘至数据库相关的配置表或任务专属JSON字段。
    *   **服务引擎层 (TaskEngine改造)**：打标引擎在启动计算任务或匹配数据记录时，需读取上述动态权重上下文。原本写死在代码内的权重常量将被替换，以形如 `RankScore(record, rule, weights)` 的方式进行动态计分。
    *   **安全与体验边界防护**：引入自定义权重后，优先级的“绝对统治权”将由数学得分（W1的相对大小）来保证，而非原本硬编码的“直接中断计算”。建议在前端 UI 加强交互提示与校验，明确提示用户：**若希望人工配置的优先级具有一票否决权，W1 的值必须设置为远大于 W2+W3 的总和**。

### 3.1 维度分解与计算机制

#### 维度 1：人为静态权重 (PriorityScore) - W1 占比极大
*   **定位**：系统的人工意志体现。
*   **机制**：提取 UI 上配置的 `Priority` 值。在引入自定义权重后，取消原本的“直接中断计算”硬编码逻辑，转而完全依靠 W1 的高权重系数来形成总分上的断层碾压。只要用户配置的 W1 足够大，`Priority` 的微小差距也能立刻决定胜负。

#### 维度 2：规则逻辑深度 (ComplexityScore) - W2
*   **定位**：越具体、限制越多的规则，画像越精准。
*   **机制**：解析 AST 树进行客观打分。
    *   **基础分**：每多一层 `AND/OR` 的 Condition 节点，基础分 `+10`。
    *   **算子置信度系数**：
        *   精确匹配 (`equals`, `==`)：系数 `x 1.5`（确信度极高）。
        *   范围/正则匹配 (`regex`, `>`, `<`)：系数 `x 1.2`。
        *   模糊包含 (`contains`)：系数 `x 1.0`。

#### 维度 3：数据置信度 (CompletenessScore) - W3
*   **定位**：数据自身的质量决定了它被打上某个标签的可信度。
*   **机制**：扫描该行数据，考察除匹配规则外，其他业务核心字段（如 `用户ID`, `注册时间`）的完整度。如果大量关键字段存在 `Null/Empty`，其置信度得分将受到乘数惩罚。我们在处理同样的冲突时，更偏好把主标签颁发给“画像丰满”的数据。

#### 维度 4：AI 语义裁判 (AIConsensusScore) - W4 (关键仲裁者，延迟计算)
*   **定位**：机器无法理解的业务互斥，交由大语言模型处理。
*   **数据隐私与合规控制 (手动开关机制)**：
    *   **由于涉及将原始数据发送至外部 LLM 接口，出于对用户商业机密和隐私数据的绝对保护，此功能默认为【关闭状态】。**
    *   用户需在【全局设置】或【规则配置台】中明确勾选并同意“允许 AI 介入深度打标裁决”后，该维度方可生效。
    *   若用户未开启该开关，当遭遇平局时，系统将退回使用默认的规则 `ID` 作为最终兜底。
*   **机制 (智能熔断与延迟计算 - 仅在开关开启且基础分相近时触发)**：
    *   为了性能与成本考量，W4 **不是**每次都会计算的。
    *   当且仅当维度 1、2、3（即 W1+W2+W3）的**基础总分计算完毕后**，如果发现两个候选规则的总分差值 **小于 5%**，这说明遇到了“神仙打架”的模棱两可数据，此时才会触发延迟计算 (Lazy Evaluation)。
    *   系统不直接判定，而是通过 `aiengine_service` 组装一次静默的 LLM 后台调用。
    *   **Prompt 构造示例**：
        > "你是一个数据风控专家。现有一条数据：`{"年龄": 20, "月消费": 50}`。它同时符合【活跃用户】和【羊毛党】的打标规则，且置信度一致。基于商业常识，哪个标签更适合作为它的主标签？请先回复 A 或 B 作为结果，并附带简短的判定理由。"
    *   AI 的判定结果将直接注入该维度的得分，成为打破平局的“金手指”。
*   **AI 介入标识与裁决透明化 (新增需求)**：
    *   **介入标识 (`is_ai_intervened`)**：在打标结果的数据模型中新增一个状态字段。当某条数据的最终归属是由 W4 (AI得分) 介入并决定胜负时，该标识置为 `true`。
    *   **裁决理由 (`ai_arbitration_reason`)**：大模型在回答时给出的判定理由将被解析并持久化。在前端的“打标结果明细”、“审核管理”等数据报表页面中，系统将显式展示 AI 介入的标记，并附带展示具体的裁决理由。此举极大地增强了定标过程的可解释性与事后审计追踪能力。

### 3.2 得分归一化与置信度百分比展示 (UI 展示体验优化)

由于公式计算出的基础得分 `FinalScore` 是一个无上限的绝对战力值（取决于用户如何设置 W1~W4），为了在前端打标结果或审核报表中向用户提供更直观的数据，需要在引擎向前端输出结果前，对碰撞的规则得分进行**百分比归一化 (Normalization)** 处理。

*   **计算机制**：提取该条数据命中的所有候选规则总分，计算单个规则得分占总碰撞分的百分比。
*   **转换公式**：`Confidence(Rule_i) = FinalScore(Rule_i) / Σ(FinalScore(候选规则集)) * 100%`
*   **应用效果**：
    *   **底层仲裁**：打标引擎依然依赖绝对总分去争胜负（比大小）。
    *   **前端展示**：在“打标结果明细”等页面，不再向用户展示冷冰冰的“15300分”这种无参照基准的数据，而是展示直观的置信度。例如：命中【高价值用户】置信度 **92.5%**，命中【价格敏感用户】置信度 **7.5%**。配合前面提到的“AI 裁决理由”，将极大拉升整个产品专业度与可解释性。

## 4. 架构实施建议

这套 `MDCT` 算法的落地非常优雅，对现有代码具有极高的兼容性：

1.  **无侵入性**：底层 `matcher.go` 的匹配逻辑和返回值完全不需要修改。
2.  **平滑替换**：只需要在 `internal/service/taskengine/taskengine_service.go` 的 `processRecords` 方法中，找到原有的简单切片排序闭包：
    ```go
    // 旧逻辑
    return matchedRules[i].model.ID > matchedRules[j].model.ID
    ```
    将其替换为调用新的计算模块（并传入动态权重）即可：
    ```go
    // 新逻辑 (weights 为从配置或上下文中读取的用户自定义权重)
    return RankScore(record, matchedRules[i], weights) > RankScore(record, matchedRules[j], weights)
    ```
3.  **AI 复用**：AI 仲裁机制可完美复用我们刚在 V3.1 完成的 `ChatWithAIStream` 或底层的 `openai.Client` 网络链路。

## 5. 总结

通过引入 `MDCT` 多维共识打标算法，TagMatrix 在遇到复杂标签冲突时，将真正实现**“特权可控、数据驱动、AI 托底”**的专业化风控决策，使这套系统的打标准确度和业务贴合度再上一个新台阶。
