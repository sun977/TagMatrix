# V4.0 优化方案：同构数据规则复用与克隆机制 (Rule Cloning & Inheritance)

## 一、 核心设计原则
1. **坚守底层解耦**：不改变数据库中 `Rule` 与 `Dataset` 1对1强绑定的物理外键关系，维护审计日志的独立性。
2. **“深拷贝”代替“换绑”**：所有复用操作在底层均表现为将源规则的 JSON 树**深拷贝**一份，生成新的 `rule_id` 并绑定给目标数据集。
3. **引入 Schema 校验网**：任何跨数据集的规则拷贝，必须前置触发“表头字段匹配度校验”，防止幽灵字段引发匹配引擎崩溃。

## 二、 方案落地：双维度交互路径

系统将提供两个维度的克隆入口，以满足不同颗粒度的复用需求：

### 路径 1：规则维度的“单点克隆” (Tag-Rule Level)
* **适用场景**：用户在给某个数据集（B）配置特定标签（如“高危泄密”）时，想直接复用昨天另一个数据集（A）里配好的那几百行复杂的条件逻辑。
* **UI 交互**：
  1. 在【规则配置】页面，选择标签并选中当前目标数据集 B，此时右侧配置区是空的。
  2. 在右上角“添加条件”旁边，新增一个 **[从历史克隆 ]** 按钮。
  3. 点击后弹出下拉框，列出该标签曾经配置过的所有历史数据集（如：数据集 A、数据集 C）。
  4. 选中“数据集 A”，前端立即将 A 的规则 JSON 渲染到当前画布。用户可以微调后点击“保存”，从而完成单条规则的复用。

### 路径 2：数据集维度的“一键继承” (Dataset Level Batch)
* **适用场景**：这是最高效的场景。例如每个月新导入一份财务报表（同构数据），需要把上个月报表绑定的 50 个标签规则，瞬间全部转移过来。
* **UI 交互**：
  1. 在【数据集】列表页面，点击刚刚导入的“10月份报表”，在操作列新增按钮 **[继承历史规则 ]**。
  2. 弹出对话框：“请选择要继承的模板数据集”。用户选择“9月份报表”。
  3. 后端服务被触发，开始执行**批量克隆流**。

## 三、 关键技术点：Schema 校验与防错机制 (核心屏障)

为了防止拷贝过来的规则里含有目标数据集没有的字段，后端/前端必须在拷贝前做一层校验拦截。

1. **自动提取依赖字段**：遍历源规则 JSON 树，提取所有 `field` 属性（如 `金额`, `IP`, `操作人`）。
2. **表头碰撞比对**：将提取出的字段，去和目标数据集的表头数组进行 `contains` 校验。
3. **三态反馈机制**：
   * **🟢 完美匹配 (100% 命中)**：源规则用到的字段在新表头里全都有，直接绿灯放行，克隆成功。
   * **🟡 降级匹配 (部分缺失)**：源规则用了 5 个字段，但新表里没有 `IP`。系统允许克隆，但用显眼的黄色高亮缺失字段所在的规则块，提示用户：“克隆成功，但 `IP` 字段不存在，请手动修改或删除该条件后保存”。
   * **🔴 结构性错误**：如果源规则绑定的完全是风马牛不相及的表，系统直接拦截提示：“表头差异过大，拒绝克隆”。

## 四、 对现有系统的影响评估
* **数据库改造**：**0 修改**。现有的 `tag_rules` 表结构完全支持这种逻辑。
* **后端引擎**：**0 修改**。匹配引擎依然读取独立的 rule json，感知不到它是怎么来的。
* **工作量**：属于**极轻量级 (Lightweight) 的 UI/API 层改造**。只需要在前端增加几个按钮组件，以及在后端写一个 `CloneRule` 的组装与校验接口即可。
