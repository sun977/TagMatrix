# V5.0 跨表打标机制 (Cross-Table Tagging) 架构蓝图

> **文档状态**：架构探讨与演进规划（草案）
> **目标阶段**：V5.0
> **核心议题**：突破单数据集（单表）的物理隔离限制，实现基于多张关联表联合数据的深度特征打标。

---

## 1. 现状痛点与业务诉求

在 V4.0 及以前的架构中，TagMatrix 引入了“数据集 (Dataset)”概念，成功解决了异构数据的隔离问题，确保了打标引擎的高效和稳定。但这同时带来了一个显著的业务痛点——**数据孤岛**。

**典型业务场景：**
*   **场景 A (风控/画像)**：系统内有两个数据集——`【用户基础信息表】` 和 `【用户订单流水表】`。运营人员希望给“过去三个月内购买过手机，且用户年龄大于 30 岁”的用户打上 `【高净值数码客】` 的标签。
*   **现状约束**：当前的打标引擎只能在一个数据集中进行条件判断（要么在用户表看年龄，要么在订单表看商品），无法同时跨越两张表进行 `AND` 逻辑的匹配。

如果强迫用户在外部（如 Excel 或 Python 脚本中）把所有数据 Join 成一张“大宽表”再导入，不仅操作门槛极高，也丧失了 TagMatrix 作为专业数据处理工具的核心价值。

---

## 2. 核心解决思路：虚拟视图 (Virtual Views) 映射

为贯彻 TagMatrix 一直以来的**“轻量、优雅、不破坏底层核心引擎”**的设计哲学，我们放弃在业务代码层实现臃肿的内存 Join，而是全面拥抱底层数据库（SQLite/MySQL）的原生能力：**利用 SQL 视图 (View) 打造“虚拟数据集”**。

### 2.1 架构设计理念
1. **引擎无感知**：底层规则 AST 引擎 (`matcher.go`) 和任务分发引擎不需要知道数据是来自单表还是跨表。它们只认“表头 Schema”和“数据行”。
2. **视图即数据集**：允许用户利用原生 SQL 将多个数据集 Join 起来，形成一个视图（View），系统将这个视图注册为一个特殊的 `SysDataset`（`type="view"`）。
3. **降维打击**：所有在单表数据集上能用的能力（规则绑定、Dry Run、甚至多维共识打标 MDCT），在视图数据集上全部自动生效。

---

## 3. 实现路径与工作流规划

### 步骤 1：构建视图工厂 (View Builder)
在 DataAdmin 模块或新建的“视图管理”UI 中，为用户提供跨表聚合的工具。
*   **高阶模式**：提供原生 SQL 编辑器，用户手写 `CREATE VIEW` 语句。由于底层是统一的 `raw_data_records` 表加动态 JSON，SQL 将大量运用提取函数：
    ```sql
    CREATE VIEW view_user_orders AS 
    SELECT 
        u.id as main_record_id,
        json_extract(u.data, '$.user_id') as user_id,
        json_extract(u.data, '$.age') as age,
        SUM(json_extract(o.data, '$.amount')) as total_amount
    FROM raw_data_records u
    JOIN raw_data_records o ON json_extract(u.data, '$.user_id') = json_extract(o.data, '$.buyer_id')
    WHERE u.dataset_id = 1 AND o.dataset_id = 2
    GROUP BY u.id;
    ```
*   **低代码模式 (可选远期演进)**：提供拖拽式的图形界面，用户选择主表、关联子表和 Join 条件，系统自动生成上述复杂 SQL。

### 步骤 2：注册虚拟数据集与 Schema 重塑 (解决表头冲突)
*   在 `sys_datasets` 表中增加字段（如 `is_view boolean`, `view_sql text`）。
*   **Schema 重塑机制**：针对跨表可能出现的“表头不同”或“字段重名”（如两张表都有 `name` 字段）问题，系统强制要求在 `CREATE VIEW` 语句中使用 `AS` 别名（例如 `u.name AS user_name`, `p.name AS product_name`）。
*   当视图建立后，系统自动执行 `SELECT * FROM view LIMIT 1`。它会将上述提取并重命名后的字段，作为一个**全新且独立的数据集 Schema** 保存到 `schema_keys` 中。规则引擎随后仅针对这套“新表头”进行匹配，彻底屏蔽底层的多表复杂性。
*   在前端的【数据集列表】中，以特殊的 Icon（如 🔗）展示该视图，它表现得就像一个真正的数据集。

### 步骤 3：规则配置与无缝打标
*   业务人员在【标签规则配置】页面，像往常一样选择这个“虚拟数据集”。
*   配置诸如 `age > 30 AND total_amount > 5000` 的规则。
*   触发打标任务时，底层的 `taskengine` 直接从该视图中拉取数据，送入 `matcher` 进行判定。

### 步骤 4：标签回流与挂载 (关键难点)
**问题**：视图是虚拟的，没有实体概念。当引擎决定给视图的一行数据打标时，这个标签 (`SysEntityTag`) 应该挂载在哪个物理记录的 ID 上？

**解决方案 (主键锚定契约)**：
*   **强制约定**：任何跨表视图**必须**暴露一个名为 `main_record_id` 的列，用来锚定此次打标的真正“主体”（比如上述例子中主体是【用户】，则指向用户表的 `raw_data_records.id`）。
*   **入库流转**：打标引擎在执行时，读取该行的 `main_record_id`，将生成的标签最终物理挂载回主表的真实数据上。
*   这样，当用户回到单表【数据看板】查看用户数据时，跨表运算得出的“高净值数码客”标签已经赫然在列。

### 步骤 5：全景宽表展示与双维度导出闭环
打标完成后，系统支持两种维度的数据验收与导出，形成完美的业务闭环：
*   **维度 A（结果回流主表导出）**：基于步骤 4 的主键锚定，标签已物理绑定至主表。用户可直接在原“单表数据集”的打标看板中，导出带有最新跨表标签的原始单表数据。
*   **维度 B（全景大宽表导出）**：由于该跨表视图已被系统完整注册为“虚拟数据集”，用户同样可以在【数据看板】的下拉框中选中该视图。系统会如常展示包含所有跨表 `Join` 聚合字段（如 `user_name`, `total_amount`）以及最新标签的**全景大宽表**。点击导出即可直接获得一份供 BI 深度分析的跨表 CSV 数据集。

## 4. AI Copilot 的深度融合

跨表 SQL 和 JSON 提取函数的编写对于非技术人员来说存在“陡峭的学习曲线”。这正是我们在 V4.0 已经全局落地的 AI Copilot 在 V5.0 将要继续发挥决定性作用的舞台。

*   **自然语言构建视图**：用户在创建视图时，可以直接向右侧的 AI 助手说：
    > *"把数据集1的用户信息和数据集2的订单记录关联起来，条件是 user_id，顺便帮我统计出每个用户的总消费金额和最后一次购买时间。"*
*   **Schema 感知注入**：AI 助手会自动读取数据集 1 和 2 的表头 Schema，利用我们在后台内置的 prompt 模板，自动输出完美的包含 `json_extract` 和正确 `dataset_id` 过滤的 SQLite 语句，并直接推送到编辑器中。

## 5. 总结

跨表打标签的引入，将使得 TagMatrix 从一个“平面化的单维打标工具”，升维成一个**“立体化、具备复杂风控和深度用户画像能力”**的企业级计算引擎。通过原生 SQL 视图配合 AI 辅助生成，我们以极低的架构修改成本，换取了极其广阔的业务拓展空间。
