# V5.0 云端协作与插件生态 (Cloud & Plugin Ecosystem) 架构蓝图（草案）

> **文档状态**：架构探讨与长线演进规划（草案）
> **目标阶段**：V5.x 长线演进
> **核心议题**：突破单机离线应用的局限，引入“去中心化的资产协作”与“无边界的模型推导能力”，将 TagMatrix 从个人效率工具升维为企业级策略平台。

---

## 1. 业务背景与演进动机

TagMatrix 在前四个大版本的演进中，将**“本地单机性能”**和**“数据隐私安全”**做到了极致（数百万数据不离本机，纯离线 SQLite 处理）。但随着业务深度的增加，新的痛点开始浮现：

1.  **协作断层**：公司内部 A 部门的专家辛辛苦苦通过 AI 调优出了一套包含 200 个节点的【高净值风控标签树】及规则，B 部门想要复用，目前只能靠微信互传 `tags.json`，存在版本混乱、极易被覆盖的问题。
2.  **算力与算法边界**：现有的匹配引擎 (`matcher.go`) 拥有强大的算子（正则、数值、包含等），擅长处理结构化数据。但如果业务诉求是：“找出评论字段中**带有愤怒情绪**的数据”或“识别描述中**包含竞品名称（需模糊语义匹配）**的数据”，传统的硬编码 AST 规则就束手无策了，这必须依赖外部的 NLP 或私有化机器学习模型。

---

## 2. 核心战役一：资产云端同步 (Cloud Asset Sync)

**设计原则：物理数据绝对隔离，仅同步策略资产。**

### 2.1 架构设计
我们不打算将 TagMatrix 改造成笨重的 Web SaaS，而是采用类似 Git 的 **分散式协作模型 (Hub-and-Spoke)**。
*   **同步协议**：系统内置标准化接口，支持对接企业内部已有的 **S3 对象存储** 或 **WebDAV** 服务。用户只需在全局设置中填入 Bucket 凭证。
*   **资产快照 (Asset Snapshot)**：所谓“资产”，特指：标签目录树 (`tags`)、规则集 (`rules`)、数据集表头 (`schema`)。系统坚决**拦截且不上传**任何具体的业务数据 (`raw_data_records`)。

### 2.2 工作流设想 (Pull / Push 机制)
1.  **资产打包 (Push)**：专家 A 在本地调优好某数据集的规则后，点击【推送到云端】。系统将该业务线的规则打包为一个具有唯一版本号的 `.tma` (TagMatrix Asset) 文件上传至 S3。
2.  **云端大厅 (Hub)**：前端 UI 新增一个【资产市场/云端库】面板，拉取 S3 中团队共享的所有资产列表。
3.  **拉取应用 (Pull)**：专家 B 在云端库看到更新，点击【拉取】。系统在本地进行比对（Diff），合并最新的标签规则，并在发生冲突时提示“保留本地”或“覆盖更新”。

## 3. 核心战役二：高阶插件化生态 (Plugin Ecosystem)

**设计原则：语言无关，跨进程通信，对核心引擎无侵入。**

### 3.1 引入 `plugin` 新算子
在现有的 `matcher` 引擎的抽象语法树 (AST) 中，我们新增一个超级算子：
```json
{
  "field": "user_comment",
  "operator": "plugin",
  "plugin_name": "sentiment_analysis_v2",
  "args": { "threshold": 0.8, "target_emotion": "angry" }
}
```

### 3.2 插件架构选型：HashiCorp `go-plugin` (RPC Sidecar)
因为 TagMatrix 是用 Go 编译的单体二进制文件，直接挂载 `.so` 动态库跨平台支持极差（Windows 基本不可用）。我们推荐采用业界标准的基于 **RPC/gRPC 的跨进程插件架构**：

1.  **运行机制**：
    *   插件本质上是一个独立的可执行文件（可以是用 Python 写的封装了 PyTorch 模型的脚本，也可以是另一个 Go 编译的程序）。
    *   TagMatrix 主进程启动时，会扫描 `./plugins` 目录，并作为 Parent 进程自动拉起这些子进程。
    *   两者通过 `stdout` 进行握手，并通过本地 gRPC 通信。
2.  **执行闭环**：
    *   当底层的打标任务遇到 `plugin` 算子时，Go 主进程通过 gRPC 将这一行的 `user_comment` 文本发送给 Python 插件进程。
    *   Python 进程调用内部加载的 NLP 模型，计算出情绪分数为 0.9，并返回 `true`。
    *   Go 引擎接管结果，继续完成后续的入库和打标逻辑。

### 3.3 插件应用场景举例
*   **Python AI 模型插件**：本地部署一个轻量级 Transformer 模型，实现“语义相似度打标”或“黄赌毒词汇过滤”。
*   **外部 API 查询插件**：写一个插件，在打标时实时调用天眼查/企查查 API，根据数据行里的“企业名称”字段，判断该企业是否“被执行人”，以此作为打标条件。
*   **特殊数据解析插件**：解析复杂格式的数据字段，例如将数据中存放的 XML 串或加密 Hash 实时解密后再参与规则判断。

## 4. AI Copilot 在 V5.x 中的深度赋能

在上述架构下，AI 将进化为**“生态总管”**：
1.  **AI 辅助合码 (Smart Merge)**：当云端拉取的规则与本地规则发生严重冲突时，AI Copilot 将介入，分析两套规则的优劣，并给出合并建议。
2.  **AI 编写插件 (Code-to-Plugin)**：如果用户需要一个特殊的外部接口打标（比如查某外部系统），只需对 AI 说：“帮我写一个 Python 插件，每行数据发一个 GET 请求到 xxx 接口提取 status 字段”。AI 自动生成符合 gRPC 契约的 Python 脚本并一键挂载到 `./plugins` 目录下，立刻生效。

## 5. 总结

云端协作与插件化是 TagMatrix 突破内生边界的两把钥匙。
*   **云端协作 (Cloud Sync)** 让策略本身具有了流动性和可复用性。
*   **插件化 (Plugin Ecosystem)** 让打标引擎的判断力从“正则表达式”跃升到了“无限的机器学习与外部算力”。
这两者的结合，将彻底奠定 TagMatrix 作为新一代“数据智能标记与资产沉淀中枢”的地位。
