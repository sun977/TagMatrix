# TagMatrix 算子与上下文引擎升级方案 (V4.0)

## 1. 背景与需求痛点
在当前 TagMatrix 架构中，`matcher` 是一个纯粹的**无状态布尔过滤器**。对于规则引擎而言，它只能回答“是”或“否”。
而在实际的打标与数据分析场景中，我们面临以下进阶需求：
1. **行级多频次挖掘**：一行数据中，某个标签的特征可能出现多次（例如“高价值”关键词在长文本中出现了 3 次），目前只能记录为命中 1 次。
2. **全局命中统计**：希望在一次打标任务结束后，直接得出“高价值”标签在全量数据中总共命中了多少次。
3. **多特征叠加计数**：一行数据如果同时满足“高风险”的 3 个不同特征（如IP黑名单、异地登录、高频操作），希望能够叠加计数（计3次），而目前的 `OR` 逻辑在命中第 1 个特征后就会短路返回。

## 2. 核心架构设计：引入 Context 状态容器
为了在**不破坏现有 AST 解析树结构**的前提下实现计数与观测，方案计划将 `matcher` 从“无状态”升级为“带上下文状态 (Context-Aware)”。

在任务引擎启动时，向 `context.Context` 中注入以下状态容器，并透传给 `matcher`：

*   **`GlobalCounter` (全局计数器)**：贯穿整个打标任务，并发安全（`sync.Map`），用于统计各个标签在所有数据中总命中次数。
*   **`RowCounter` (行级计数器)**：生命周期为“单行数据处理期间”，用于统计当前行中各个标签命中的具体频次。
*   **`CurrentTag` (当前标签上下文)**：引擎执行规则时，动态注入正在评估的 TagName，使算子知道该给谁记数，从而避免在 JSON 规则中硬编码标签名。

## 3. 算子库升级：新增“副作用 (Side-Effect)”算子
原有的算子（如 `equals`, `contains`）只做条件判断。我们将新增两类带有副作用的算子，它们在判断命中时，会自动将计数写入 Context。

### 3.1 频次挖掘型算子（针对文本多次出现）
*   **`count_contains`**：统计指定子串在字段中出现的次数。
*   **`count_regex`**：统计正则表达式在字段中成功捕获的次数。
*   **执行逻辑**：不仅返回 `true`/`false`，若出现次数 $N > 0$，会自动为 `CurrentTag` 的 `RowCounter` 和 `GlobalCounter` 加 $N$。

### 3.2 逻辑标记型算子（针对非文本复合规则）
*   **`row_inc`**：无条件返回 `true`，并为当前标签的行级计数器 +1。
*   **`global_inc`**：无条件返回 `true`，并为全局计数器 +1。
*   **执行逻辑**：通常放置在 `AND` 数组的最后，利用 `AND` 前置遇假短路的特性。只有当业务条件全部满足时，流程才会执行到该标记算子进行计数。

## 4. AST 节点扩展：支持非短路合并
为了解决多特征叠加计算时的 `OR` 短路问题，扩展一个新的分支节点：
*   **`evaluate_all` (或 `evaluate_all_or`)**：
    *   区别于原有的 `OR`（遇到第一个 `true` 就中止），该节点会**强制遍历并执行内部所有的子规则**。
    *   作用：保证行数据同时命中多个特征时，每个特征的计数算子都能被执行，实现同一标签叠加计数。

## 5. 规则配置示例

### 场景 1：单字段多次出现计数（频次挖掘）
**需求**：判断 `content` 字段是否包含“高价值”，并记录出现的次数。
```json
{
  "field": "content",
  "operator": "count_contains",
  "value": "高价值",
  "ignore_case": false
}
```

### 场景 2：非文本条件的复合计数
**需求**：如果“账户余额 > 10000”且“状态为活跃”，则触发计数。
```json
{
  "and": [
    {
      "field": "balance",
      "operator": "greater_than",
      "value": 10000
    },
    {
      "field": "status",
      "operator": "equals",
      "value": "active"
    },
    {
      "operator": "row_inc",
      "value": 1
    }
  ]
}
```

### 场景 3：多特征叠加计数（解决短路问题）
**需求**：黑名单IP、异地登录、正则报错，只要满足任意一个就计1次。若同时满足，则叠加计数。
```json
{
  "evaluate_all": [
    {
      "and": [
        {"field": "ip", "operator": "in", "value": ["1.1.1.1", "2.2.2.2"]},
        {"operator": "row_inc", "value": 1}
      ]
    },
    {
      "and": [
        {"field": "login_location", "operator": "equals", "value": "异地"},
        {"operator": "row_inc", "value": 1}
      ]
    },
    {
      "field": "error_log",
      "operator": "count_regex",
      "value": "failed_login"
    }
  ]
}
```

## 6. 系统改造影响面评估

1.  **`internal/pkg/matcher/matcher.go` (核心影响)**：
    *   为 `Match` 和 `evaluateCondition` 增加 `context.Context` 参数透传。
    *   在 `MatchRule` 结构中新增 `EvaluateAll []MatchRule` 字段。
    *   在 `evaluateCondition` 中扩展 `count_contains`, `count_regex`, `row_inc` 算子逻辑。
2.  **`internal/model/dto.go` (模型影响)**：
    *   `TaggedRecordDto` 新增 `TagHits map[string]int`，用于前端展示该行数据中各标签的命中频次。
    *   后续可基于计数值，在 Mixed 模式下自动推举 `PrimaryTag`。
3.  **`internal/service/taskengine/taskengine_service.go` (引擎影响)**：
    *   初始化 `GlobalCounter` 与 `RowCounter`。
    *   处理规则前将当前 TagName 注入上下文。
    *   收集计数并封存到结果中进行落盘。

---
**设计结论**：该方案具备高度扩展性与优雅性，完全复用现有 AST 模型，只需极小范围内的接口重构，即可将匹配器算力提升至具有副作用管理的高阶状态。
