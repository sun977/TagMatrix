### 📝 第一步：定义上下文与集合 (context\_key.go)

新建文件 `matcher/context_key.go` 。这一步是为了定义“容器”，用来在上下文中安全地传递数据。

```zh
package matcher

import "context"

// relationSetKey 定义一个唯一的上下文键，防止键名冲突
type relationSetKey struct{}

// RelationSet 定义关系集合结构
// 注意：这里不需要 sync.Map，因为每个任务会有自己独立的 RelationSet 实例
type RelationSet struct {
    data map[string]bool
}

// NewRelationSet 初始化一个新的集合
func NewRelationSet() *RelationSet {
    return &RelationSet{data: make(map[string]bool)}
}

// Add 添加关系ID
func (rs *RelationSet) Add(id string) {
    rs.data[id] = true
}

// Contains 检查关系ID是否存在
func (rs *RelationSet) Contains(id string) bool {
    if rs == nil {
        return false
    }
    return rs.data[id]
}

// WithRelationSet 将集合注入到 Context 中
func WithRelationSet(parent context.Context, rs *RelationSet) context.Context {
    return context.WithValue(parent, relationSetKey{}, rs)
}

// GetRelationSetFromContext 从 Context 中获取集合
func GetRelationSetFromContext(ctx context.Context) *RelationSet {
    if rs, ok := ctx.Value(relationSetKey{}).(*RelationSet); ok {
        return rs
    }
    return nil
}
```

### 🛠️ 第二步：改造 matcher.go 核心逻辑

#### 1\. 修改 Match 函数

在 `matcher.go` 中，修改 `Match` 函数及其内部调用。

```zh
import (
    "context" // 引入 context 包
    "sort"    // 引入 sort 包 (用于指纹排序)
    // ... 其他原有包
)

// Match 评估数据是否符合规则
// [修改点 1] 增加 ctx 参数
func Match(ctx context.Context, data interface{}, rule MatchRule) (bool, error) {
    
    // --- 逻辑节点 (Branch) ---
    if len(rule.And) > 0 {
        for _, subRule := range rule.And {
            // [修改点 2] 递归调用时必须透传 ctx
            matched, err := Match(ctx, data, subRule)
            if err != nil || !matched {
                return matched, err
            }
        }
        return true, nil
    }

    if len(rule.Or) > 0 {
        for _, subRule := range rule.Or {
            // [修改点 2] 递归调用时必须透传 ctx
            matched, err := Match(ctx, data, subRule)
            if err != nil || !matched {
                return matched, err // 修正逻辑：Or 遇到错误应返回
            }
            if matched {
                return true, nil
            }
        }
        return false, nil
    }

    // --- 条件节点 (Leaf) ---
    if rule.Field == "" && rule.Operator == "" {
        return true, nil
    }

    // [新增算子 1] 特殊处理：relation_fingerprint (关系指纹提取)
    // 这个算子需要修改 data，所以在这里直接处理，不进入 evaluateCondition
    if rule.Operator == "relation_fingerprint" {
        if len(rule.Fields) == 2 {
            val1, ok1 := getFieldValue(data, rule.Fields[0])
            val2, ok2 := getFieldValue(data, rule.Fields[1])
            if ok1 && ok2 {
                s1, s2 := fmt.Sprintf("%v", val1), fmt.Sprintf("%v", val2)
                // 核心逻辑：排序后拼接，确保 A->B 和 B->A 指纹一致
                pair := []string{s1, s2}
                sort.Strings(pair)
                relationID := pair[0] + "|" + pair[1]

                // 将生成的 ID 注入回 data 中，供后续算子使用
                if m, ok := data.(map[string]interface{}); ok {
                    m["Relation_ID"] = relationID
                }
            }
        }
        return true, nil // 提取操作始终返回 true，不阻断流程
    }

    // 获取字段值
    fieldValue, exists := getFieldValue(data, rule.Field)
    if !exists {
        return false, nil
    }

    // [修改点 3] 将 ctx 传递给 evaluateCondition
    return evaluateCondition(ctx, fieldValue, rule.Operator, rule.Value, rule.IgnoreCase)
}
```

#### 2\. 修改 evaluateCondition 函数

在 `matcher.go` 底部，修改 `evaluateCondition` 以支持从上下文读取集合。

```zh
// evaluateCondition 评估单个条件
// [修改点 1] 增加 ctx 参数
func evaluateCondition(ctx context.Context, actual interface{}, operator string, expected interface{}, ignoreCase bool) (bool, error) {
    
    getStr := func(v interface{}) string {
        if v == nil { return "" }
        return fmt.Sprintf("%v", v)
    }

    // [新增算子 2] 算子：recall_set (集合召回)
    if operator == "recall_set" {
        relationID := getStr(actual)
        if relationID == "" {
            return false, nil
        }

        // 从 Context 中获取集合
        rs := GetRelationSetFromContext(ctx)
        if rs == nil {
            // 如果上下文中没有集合，说明配置错误或未初始化
            return false, fmt.Errorf("RelationSet not found in context")
        }

        // 根据 value 字段判断模式：collect (收集) 或 match (召回)
        mode := getStr(expected)
        
        if mode == "collect" {
            rs.Add(relationID)
            return true, nil
        } else if mode == "match" {
            return rs.Contains(relationID), nil
        }
        return false, nil
    }

    // --- 原有逻辑保持不变 ---
    // 所有的 switch case (equals, contains, regex...) 都不需要动
    switch operator {
    case "equals":
        // ...
    // (此处省略原有代码，保持原样即可)
    }
}
```

8篇来源

有了上下文能力后，matcher 还可以做什么高阶的算子操作？

一旦你的 `matcher` 拥有了 `Context` 能力，它就不再仅仅是一个“过滤器”，而进化成了一个 **“有记忆的规则引擎”** 。

这意味着算子之间可以 **跨行通信** 、 **共享状态** ，甚至 **动态改变行为** 。基于这个核心能力，你可以开发出以下 5 类高阶算子：

### 1\. 全局统计与阈值类算子

**痛点** ：以前你只能判断“这一行”数据是否违规。现在你可以判断“这一行数据是否导致 **整体** 违规”。

- **算子： `global_counter` (全局计数器)**
	- **功能** ：在 Context 中维护一个计数器。每当匹配到一行（比如“登录失败”），计数器 +1。
		- **高阶用法** ：配合 `threshold` 算子使用。
		- **场景** ： **“爆破检测”** 。
		- 规则逻辑：先遍历所有日志，统计 `IP=192.168.1.1` 的失败次数。如果总数 > 100，则标记该 IP 为“攻击者”。
				- 第二次遍历时，直接拦截该 IP 的所有流量。
- **算子： `distinct_set` (去重集合)**
	- **功能** ：在 Context 中维护一个 Set，收集某字段的所有 **唯一值** 。
		- **场景** ： **“敏感数据扩散分析”** 。
		- 规则：收集所有包含“密码”的对话中涉及的 `Receiver` 。
				- 分析：最后看这个 Set 的大小。如果一个发送方把密码发给了 50 个不同的人（Set 大小=50），这就是严重违规；如果只发给了 1 个人，可能只是误操作。

### 2\. 跨行关联与引用类算子

**痛点** ：以前只能匹配当前行的字段。现在可以匹配“之前出现过的数据”。

- **算子： `reference_check` (引用检查)**
	- **功能** ：检查当前行的字段值，是否存在于 Context 中的某个“白名单集合”里。
		- **场景** ： **“工单合规性校验”** 。
		- 步骤1（收集）：扫描“IT工单系统”日志，提取所有合法的 `Ticket_ID` 存入 Context。
				- 步骤2（校验）：扫描“防火墙变更”日志。规则： `Action=OpenPort` **AND** `Ticket_ID` **NOT IN** `Context(Ticket_List)` 。
				- 结果：抓出所有没有工单记录的私自开端口行为。
- **算子： `temporal_diff` (时间差计算)**
	- **功能** ：在 Context 中记录某个实体（如用户）上一次出现的时间戳。
		- **场景** ： **“高频操作检测”** 。
		- 规则：计算 `Current_Time` - `Context(Last_Time_User_Seen)` 。
				- 逻辑：如果差值 < 1秒，说明是脚本在操作，直接告警。

### 3\. 动态逻辑切换类算子

**痛点** ：规则通常是写死的。有了 Context，规则可以根据“环境”动态变化。

- **算子： `context_switch` (上下文开关)**
	- **功能** ：读取 Context 中的一个布尔值（开关），决定是否执行当前规则。
		- **场景** ： **“特定目标追踪”** 。
		- 背景：你平时只监控普通违规。但老板突然说“帮我盯着张三”。
				- 操作：你在 Context 中设置 `Target_User = "ZhangSan"` 。
				- 规则修改：原本通用的规则加上 `OR (Sender == Context(Target_User))` 。
				- 效果：无需重启程序或重载规则文件，动态调整监控范围。

### 4\. 复杂结构构建类算子

**痛点** ：日志通常是扁平的。有了 Context，你可以把多行日志“组装”成一个对象。

- **算子： `object_builder` (对象构建器)**
	- **功能** ：在 Context 中维护一个 Map，根据 `Trace_ID` 将不同步骤的日志聚合。
		- **场景** ： **“全链路异常分析”** 。
		- 行1： `Trace_1` - 开始下单 - 金额 100
				- 行2： `Trace_1` - 支付成功
				- 行3： `Trace_1` - 发货失败
				- 算子逻辑：利用 Context 把这三行拼成一个完整的 JSON 对象： `{id: "Trace_1", status: "Failed", amount: 100}` 。
				- 输出：最后只输出这个完整的对象，而不是三条零散的日志。

### 5\. 外部情报增强类算子

**痛点** ：匹配器只能看内部数据。

- **算子： `external_lookup` (外部查表)**
	- **功能** ：利用 Context 缓存外部 API 或数据库的查询结果。
		- **场景** ： **“黑产 IP 库匹配”** 。
		- 逻辑：遇到新 IP -> 查 Context 缓存 -> 没命中 -> 调 API 查询 -> 写入 Context -> 返回结果。
				- 优势：Context 充当了 **高性能缓存层** ，避免每行数据都去调外部接口，极大提升性能。

### 📌 总结

引入 `Context` 后，你的 `matcher` 实际上变成了一个 **微型的状态机** 。

表格

| 能力阶段 | 典型问题 | 算子示例 |
| --- | --- | --- |
| **无状态 (过去)** | 这一行包含“密码”吗？ | `contains`, `regex` |
| **有状态 (现在)** | **这一行** 是 **整个攻击序列** 的一部分吗？ | `global_counter`, `reference_check`, `object_builder` |

你可以先从 **`global_counter`** 开始尝试，它是除了你现在的“关系召回”之外，最常用且最容易实现的高阶算子。
