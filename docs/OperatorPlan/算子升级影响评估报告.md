# TagMatrix 算子升级方案影响面评估报告

## 一、 现有的代码和功能会受什么影响？

**核心结论：完全向下兼容，对现有功能“零破坏”，性能影响极小。**

1. **对旧规则的兼容性：100% 兼容**
   我们在 `MatchRule` 结构体中仅新增了 `EvaluateAll` 字段，以及在 `switch` 中新增了几个 operator。现有的 JSON 规则在解析时，由于不存在新字段，会自然走到原有的 `And` / `Or` / `Leaf` 逻辑分支，原有规则运行完全不受影响。
2. **对性能的影响：微乎其微**
   `context.Context` 的传递在 Go 中是指针级别的操作，开销极低。原有的无状态算子（如 `equals`, `contains`）执行路径没有变长，仅仅是多传递了一个 ctx 参数。
3. **对编译的影响：短暂报错，补齐参数即可**
   由于核心引擎 `matcher.Match` 的函数签名发生改变（增加了 `ctx` 参数），所有调用了该函数的地方（目前主要是 `taskengine_service.go`）在修改完成前会出现编译报错。开发时只需统一传入 `ctx` 即可解决。

## 二、 代码修改量多大，哪些地方需要修改？

**核心结论：代码修改量极小（属于微创手术），整体新增与修改代码约 100~150 行左右。**

具体需要修改的范围与细节如下：

1. **`internal/pkg/matcher/context.go`（新增文件，约 40 行）**
   * 定义存放全局计数器、行级计数器的结构体（内部封装 `sync.Map` 或 `sync.Mutex` 保证并发安全）。
   * 定义向 `Context` 注入（`With...`）和提取（`Get...`）计数器的辅助函数。

2. **`internal/pkg/matcher/matcher.go`（核心修改，约 50 行）**
   * **函数签名**：`Match` 和 `evaluateCondition` 增加 `ctx context.Context` 参数，并补齐递归调用里的参数。
   * **新增 AST 节点**：在 `MatchRule` 结构体里增加 `EvaluateAll []MatchRule json:"evaluate_all,omitempty"`。
   * **解析新节点**：在 `Match` 函数中，加入处理 `EvaluateAll` 的分支逻辑（强制遍历执行所有子规则，不短路）。
   * **算子逻辑**：在 `evaluateCondition` 函数的 `switch` 中，增加 `count_contains`、`count_regex`、`row_inc` 对应的 case 处理逻辑，并在命中时将数值写入 ctx。

3. **`internal/model/dto.go`（模型修改，约 2 行）**
   * 在 `TaggedRecordDto` 中新增字段：`TagHits map[string]int json:"tagHits,omitempty"`，用于前端展示频次信息。

4. **`internal/service/taskengine/taskengine_service.go`（调用方修改，约 30 行）**
   * 在打标任务启动前，初始化 `GlobalCounter` 实例。
   * 在处理每一行数据（Row）的循环内，初始化 `RowCounter`。
   * 组装 `ctx` 并传入 `matcher.Match(ctx, row, rule)`。
   * 匹配结束后，从 `RowCounter` 提取该行的各标签计数值，赋值给该行数据的 `TagHits`，最终随结果落库。

## 三、 架构定性：修改之后，匹配器还是之前那种“无状态”的吗？

这是一个非常关键的架构问题。
**答案是：匹配器（引擎本身）依然是无状态的，但它的“执行过程”变得有状态（Context-Aware）和带副作用（Side-Effecting）了。**

这种转变的本质如下：

1. **引擎依然无状态（Stateless Engine）**：
   `matcher` 包里面依然没有任何全局变量、没有加锁逻辑、没有任何实例属性。它依然是一个“纯函数”风格的处理器。你依然可以安全地开启 10000 个 Goroutine 并发调用 `matcher.Match`，只要它们传入的数据和上下文不冲突，引擎本身绝对不会产生数据竞争或状态污染。

2. **状态被剥离到了上下文（State in Context）**：
   * 原有模式：`f(输入, 规则) -> 结果`
   * 升级模式：`f(输入, 规则, 外部给的黑板) -> 结果，并在黑板上记一笔`
   状态并没有存储在引擎内部，而是存储在调用方传入的 `Context` 这个“黑板”里。

**总结**：
这种设计是 Go 语言非常经典的并发设计模式。它完美保留了原有匹配器**高并发、易测试、松耦合**的“无状态引擎”优势，同时巧妙地通过 `Context` 获得了**业务记录和状态观测**的高阶能力。
